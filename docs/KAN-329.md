# KAN-329: active-view reads and Calendar windows

Candidate for controller acceptance; not a deployment receipt.

Only optional domain scheduling and date demand change. The existing Jev
prototype panel remains a data consumer only while open; registering its three
required domains preserves its current commands without background reads on a
closed Dashboard. No voice capability is introduced. Providers remain keyed
by the existing signed-in session boundary, with no new persistent cache,
service endpoint, backend code, database object, MCP operation or account-data
shape. The existing semantic agent interfaces are unchanged; browser fetch
scheduling adds no business operation requiring another agent capability.

Dashboard's shared Profile/Prayer/Tasks/Progress/Momentum/Clock reads remain active.
Clock has a global timer-alarm consumer even off its own view; a cold-Dashboard
running-timer regression failed with Clock demand restricted and passes when
that required shared dependency is preserved.
Demand classification must include background side effects and open overlays,
not just page render consumers. The Clock alarm and existing panel command
regressions are the retained proof for that boundary.
The delayed first-Calendar-read/navigation regression also reproduces an
unpublished response being marked fresh after leaving the view. A request-key
change during an in-flight read now invalidates it even while inactive; return
loads the window again. Completed warm revisits still reuse confirmed data.
The mobile selected-day panel also stays inside the requested week/month after
navigation. Its previous out-of-window date could falsely show an empty day
once reads were narrowed; the responsive regression failed before the fix.
Optional domain ownership and the ten-minute freshness interval are documented
in `page-loading.md`. Calendar uses its existing authenticated
`GET /api/calendar/v1/calendar?from=...&to=...`, with all accounts and sources
preserved. The accepted provider's EventService adds a day on each side for
zone-safe filtering; no provider changes are needed. Agenda navigation preserves
access beyond the first 30 days. Sync scheduling stops off-page; provider sync
optimizations remain KAN-330, Prayer changes KAN-331, and full-day egress proof
KAN-332.

## Evidence boundary

The isolated signed-in HTTPS-service fixtures exercise the actual browser app,
service clients, response contracts, SSE parsing and two independent browser
contexts. They neither use human records nor establish hosted/live acceptance.

The same browser request scenario reproduces baseline optional-domain reads on
Dashboard and the old 766-day Calendar range. The candidate records no unrelated
Dashboard domain reads, one first visible-week request, zero extra warm-revisit
reads, bounded date navigation, and one narrow read per context after a saved
change. Content-free evidence records methods, paths, dates and counts only;
these are request measurements, not transferred-byte or full-day usage claims.

Focused hook regressions cover deferred activation, StrictMode/concurrent
single-flight, freshness expiry, inactive invalidation, coalesced reconnects,
in-flight changes, latest-window continuation, account-instance isolation,
failed reads and failed-write reporting. The inactive-read regression fails
against the exact baseline loader. Browser checks cover signed-in loading,
confirmed, empty and refusal states at 390/768/1440 pixels, keyboard event
opening, no horizontal page overflow and <=1px view-control movement. Existing
Dashboard progressive-loading, Calendar write/renewal, daily-goal and editor
keyboard/scroll regressions remain required.

The immutable candidate, focused results, pre-push gate, request/render files,
and SHA-256 receipts are carried in the external completion handoff. A focused
run affected by a temporary baseline source swap is excluded from final proof;
subsequent verification runs against stable candidate bytes. Full validation is
the installed pre-push hook (`npm run check`), once for the frozen candidate.
One initial full-gate candidate was rejected (five unit and four browser
failures): a disabled-to-enabled loader flight, outdated Calendar fixture
readiness, a formerly global Employment-load expectation, and missing demand
from the existing optional panel. The replacement batches those repairs, adds
the readiness-transition regression and keeps the rejected receipt.
Normal ready CI, protected promotion, Pages/functions deployment, final
signed-in live acceptance and release rollback belong to the controller/Sol.

# Feature Status

Use this matrix when updating documentation or UI copy. `real` means the hosted website has an implemented path; `paused` means provider work is intentionally disabled; `unavailable` means there is no supported connection; `contract-only` means a reviewed implementation boundary exists but no connector is live; `placeholder/simulated` means the integration is intentionally not presented as live; `required-gap` means policy requires the capability but the implemented path is not yet available.

| Area | Status | Notes |
| --- | --- | --- |
| Hosted GitHub Pages website | `real` | The browser website is the only supported Sabah One product runtime. Release detection runs before account loading, with existing pending-write, editor, draft, and hidden-tab reload guards. Failed initial account loads expose an explicit Retry connection and truthful bounded-retry guidance. Protected promotion, Pages and Supabase deployment, and handoff verification require the current candidate's tested tree and latest successful evidence; missing or stale receipts fail closed. |
| Account data through the services | `real` | Every domain loads and saves through its Spring service (profile, prayer, calendar, life admin, knowledge, planner, finance); open tabs reload a domain when the live-update stream reports a change. Transient failures keep the same account's confirmed data and drafts with a visible error and retry; while the browser is offline, pages are read-only under an Offline banner. Account changes remount every provider, clearing the previous account's data. Since v0.2.206 the generic Supabase record store (account snapshots, change metadata, the mutation RPCs and private Realtime Broadcast) and the first per-domain agent RPCs are retired; Supabase keeps sign-in, Vault secrets and agent OAuth approvals. No offline writes or persistent account-data cache. |
| Page loading | `real` | Each domain provider loads its own data from its service once per signed-in session and keeps it in memory; navigating reuses it. A page shows `Loading page data...` until the services it needs have answered. See `page-loading.md`. |
| Encrypted Secrets vault | `real` | The signed-in Secrets surface stores searchable account metadata and encrypted values through Supabase Vault RPCs. Values are masked, revealed one at a time, cleared from browser UI state when hidden or the session changes, and excluded from records, logs, and exports. The page reloads its summaries after its own writes and whenever it is focused or shown again. Archive and Restore are reversible; bulk export, sharing, autofill, and permanent deletion are absent. |
| Jev voice prototype | `contract-only` | New opt-in product decision on 2026-10-09: Deepgram streaming for Brave, Jev page navigation and item finding, and previewed task add/complete with planner confirmation. Provider keys remain in account-owned Vault; the browser receives only a short-lived speech token. Real Jev decisions and synthetic browser flows are checked; paid Deepgram/Brave microphone acceptance remains pending provider setup. Task and Knowledge external MCP capabilities remain explicit acceptance blockers for general agent access. See [prototype](jev-voice-prototype.md). |
| Google Calendar OAuth | `real` | Multi-account Calendar connects through Google's consent popup; the calendar service exchanges the code with Google and keeps each refresh token encrypted (AES-256-GCM) in its own database; the Supabase credential function was retired in Phase 3. Reconnect is explicit and account-scoped and never replaces the Sabah One session. |
| Supported integration setup | `real` | The offered Google Calendar integration always shows; the profile service (`/api/profile/v1/integrations`) holds each provider's saved connection record (Google only), and the retired `integrations` account collection is no longer read or written. The display shows one supported card per provider and never saves its filtered projection. Missing Google deployment configuration points to the site operator, not a nonexistent Settings field. |
| Google Calendar sync | `real` | The Spring Boot calendar service mirrors Google (60 days back, a year ahead) when Calendar loads stale, every 15 minutes while open, and on **Sync**. A calendar that fails keeps its events; accounts show `needs_reconnect` when Google refuses the credential. Event writes to Google calendars go to Google first and are shown only once confirmed; read-only calendars cannot take events. |
| Google Calendar diagnostics | `real` | Accounts show sync time, sync errors and reconnect state; Debug shows calendar-service and database health. |
| Manual calendar accounts | `real` | Local accounts, calendars and events live in the calendar service; every change is confirmed by the service before it shows. |
| Account app time zone | `real` | Settings supports an optional validated IANA zone with `Automatic` browser fallback. Generic app and Calendar time use one resolver; prayer calculations remain bound to the timetable zone and mismatches are labelled. |
| Tasks daily rollover | `real` | The planner service (`/api/planner/v1`, since v0.2.205) reopens completed daily habits and ends a missed streak once per new day, by itself every few minutes and whenever the app tells it the user's time zones (`useDailyTaskRollover`, on load and when the app or prayer day changes). Daily habits follow the app time zone; prayer habits follow the prayer timetable's zone and wait until it is known. XP, streaks and badges are awarded by the service when a task completes (a habit once a day) and when the prayer service records a prayer (exactly once); the app only shows them. |
| Recoverable core interactions | `real` | Secret, Trip wizard and Task editors confirm dirty dismissal and retain existing save semantics; the shared dialog hook manages focus and Escape. Calendar and Knowledge open actions are native buttons with separate actions; More contains and returns focus. Health removal requires confirmation. |
| Operational diagnostics | `real` | Debug → Operations shows a bounded redacted session timeline, disconnect/read/write counters and correlated recovery timings, with JSON export. An independent bounded queue sends normalized metadata with the user's bearer token to the profile service (`/api/profile/v1/operational-events`), which turns it into metrics; the Supabase `operational-events` function is retired. Account changes clear local diagnostics; collection failure never gates product operations. Scheduled public synthetic probes publish actionable GitHub status and retained receipts without a live user session. See [availability operations](availability-operations.md) for retention limits, controlled faults, infrastructure evidence and recovery objectives. |
| Global Inventory | `real` | Owned and Needed records live in the Spring life admin service (`/api/life/v1/inventory`, since v0.2.201); they support search, filters, dimensions, specifications, stock changes, acquisition (one service transaction), archive, and reviewed multiline import. Projects link to the same catalogue by stable key. |
| Inventory planning boundary | `real` | The authenticated `sabah-one-inventory-mcp` Edge Function exposes seven narrow Inventory tools through Supabase OAuth; it forwards the agent's OAuth token to the life admin service, which reads and writes the records and re-checks the Inventory approval on every request (project resolution asks the knowledge service). Before each request the function asks the life service whether the agent is approved: a refusal is the OAuth 403 challenge. It does not expose Secrets, finance, calendars, chats, settings, or broad mutations. |
| Employment application tracker | `real` | Applications live in the life admin service (`/api/life/v1/jobs`, since v0.2.201). The Employment tab opens with a compact active-application overview grouped by company, coloured stage labels, next steps, and a visible last-updated date sourced from recorded recruiting activity. All includes closed applications; search and optional filters narrow the list. Each role expands its full details, compensation, remote evidence, notes, editor, and contact history directly beneath that application. The same account-owned application IDs, semantic mutations, and three confirmed seed records are retained; import timestamps do not masquerade as recruiting dates. |
| Employment external agent access | `real` | Six semantic application/history tools use a separate Employment OAuth approval; `sabah-one-employment-mcp` forwards the agent's token to the life admin service, which re-checks that approval (the function's access check is a one-application read of the job list). Browser and agent edits share semantic mutations; retries are idempotent and revocation blocks subsequent access. Scheduled Codex agents reconcile recruiting sources after their Employment connection is authorized. |
| Cross-feature external agent access | `required-gap` | `docs/agent-access.md` makes domain-scoped MCP the required external AI interface. Inventory and Employment have separate external domains; other features must add a narrow MCP contract when materially changed. Secrets remain intentionally excluded. |
| User-facing service health | `real` | Dashboard and Settings show the Supabase session, service and Google Calendar readiness with actionable reconnect or unavailable states. |
| Night Compass prayer-first dashboard | `real` | Dashboard renders the canonical five-prayer sequence first, followed by one of 206 curated Quran passages, Learn and Move progression, and one compact Tasks route. The reading card shows full Tanzil Arabic and complete Saheeh International English from Quran.com's public API side by side at every screen width, with a reference, translator credit and source links. The shuffled 206-day cycle uses every passage before repeating and stays consistent across refreshes and devices; 133 passages concern prayer, remembrance or dua. Prayer, Learn and Move achievements use a compact top-right receipt, inset from device safe areas, with no screen-wide glow or input blocking; phones keep the same compact layout at the top. See `quran-motivation-review.md` for the selection review, Arabic text-integrity receipt and English provider-response checks. English loading failures keep the Arabic visible and offer Retry and the matching Quran.com edition link; provider text is not bundled or stored. |
| Private product usage analytics | `real` | Signed-in session, navigation, action, outcome, error, and performance events use a typed content-free taxonomy and bounded non-blocking browser batching, stored idempotently by the profile service (`/api/profile/v1/activity`, since Phase 3). The private Activity viewer has owner-only filters and shows the service's computed trends, funnels, coded errors, cold-start handling, and evidence-labelled recommendations with confidence and suggested action; it never acts automatically. Raw domain values, credentials, and provider payloads remain rejected. |
| Daily Learn and Move progression | `real` | Signed-in accounts have versioned templates, five cumulative levels, local-date progress logs, editable prayer-relative anchors, account-owned preferences, one snooze, and visible in-app states for unavailable schedules. Progress buttons default to adding the remaining amount for the displayed level target. Each section has an independent, view-local “Add individual steps” switch for one page, minute, or round at a time; reopening the dashboard restores goal completion mode. Existing account progress and five-level rules are unchanged. Each newly crossed L1–L5 threshold receives a restrained visual receipt; ordinary increments stay quiet and reduced-motion keeps the same meaning. |
| Dashboard focus ranking diagnostics | `retired` | KAN-308 removes the unused provider, recommendation requests, timers, ranking and Debug trace. Night Compass retains its domain-driven behavior. Startup clears only the two retired browser caches; historical feedback remains compatible. See `audits/2026-09-07.md`. |
| Prayer times, outcomes, deadlines, and reminders | `real` | `PrayerProvider` owns validated Jafari times, service-backed outcomes, the in-app banner and diagnostics. Asr can be checked off from Dhuhr time and Isha from Maghrib time; each prayer stays independent for combined or separate prayer. The browser and prayer service share these completion rules without changing timetable or reminder times. External-agent acceptance remains blocked by the missing Prayer MCP (see `agent-access.md`). Every reminder (deadline, prayer opportunity and Learn/Move) is decided and timed by the prayer service: the app loads the active ones on start (`GET /reminders`), receives new ones over the live-update stream (`prayer.notice`, and `prayer.reminder` for deadlines), and snoozes through the service (one snooze each, refusals shown in the service's words). The app sends the Learn/Move reminder preferences and the latest completed Level 1 date whenever they change, keeps no reminder timers or receipts, and no longer reads or writes the `prayerTracking` account record (decode-only). Web Notifications are shown only after explicit permission, with the in-app banner as the fallback. Reminders reach open tabs only. |
| Spring prayer and profile services | `real` | When `VITE_PRAYER_API_BASE_URL` and `VITE_PROFILE_API_BASE_URL` are set, the Spring Boot prayer service is the source of truth for prayer outcomes and tracking (one-time import of the account's existing history), and the profile service owns city, country and display time zone (seeded once from Settings) plus the cross-device app preferences (theme, data retention, telemetry, default calendar view, goal tags) and integration records; these are no longer stored in the `settings`/`integrations` account collections, and device-only settings stay in the browser. Saved data shows immediately and the service's data merges in; every change is sent in order and retried, and sync failures show on the Dashboard. Supabase keeps a mirror copy, so unsetting the URLs restores the previous path. Rewards and tasks moved to the planner service, and reminders are the prayer service's. Contract fixtures in `contracts/` are verified against both apps; see `contracts/README.md`. |
| Spring Calendar service | `real` | `sabah-one-services` calendar service (`/api/calendar/v1`) is the system of record for calendar accounts, calendars and events, and imported the calendar previously kept in `helm_records`. Contracts: `contracts/calendar-service`. The Dashboard also checks its health endpoints. |
| Live updates across tabs and devices | `real` | Every change a Sabah One service saves is announced on its server's RabbitMQ; the live-update gateway (`/api/live/v1/events`, one per server) streams each user's changes to their open tabs over server-sent events, authenticated with the Supabase token, and each tab reloads the changed domain (planner, knowledge, life admin, calendar, prayer, finance and equity). A tab that reconnects reloads what it may have missed. Since v0.2.205. |
| Clock surface | `real` | Timers and stopwatches are owned by the planner service (`/api/planner/v1/clock`): each change saves the one stopwatch or timer it changed, and only an item removed in the app is deleted. Custom cards, laps, alarms, and acknowledgement-required alerts. |
| Finance accounts, budgets, and savings goals | `real` | Manual accounts, transactions, budgets and savings goals live in the Spring finance service (`/api/finance/v1`, Phase 5), one record per change with an Idempotency-Key. The service works out every transaction's balance effect (a save or removal answers with the accounts it changed); the app does no balance arithmetic. One budget per category; removing an account removes its transactions and unlinks its savings goals. The old `financeAccounts`, `transactions`, `financeBudgets` and `savingsGoals` collections are decode-only and were imported once by the service. |
| Finance Stocks and Options | `real` | Separate dated holdings, plans, conditional vesting/deadlines and option scenarios, kept by the finance service (`/api/finance/v1/equity/positions`, Phase 5; the `equityPositions` collection is decode-only). Edits and removals carry the position's `updatedAt` and a stale one is refused. The Equity MCP forwards the agent's OAuth token to the same service. Protected deployment and authenticated personal-record import/readback passed at v0.2.159 on the previous store; see `finance-equity.md`. |
| Finance banking review and loans | `real` | Private dated monthly cash flow, current and conditional target budget calculations, high-value spending groups and lender records through a separate Finance MCP. The review is kept by the finance service (`/api/finance/v1/review`, Phase 5; the `financeReviews` collection is decode-only) and the Finance MCP forwards the agent's OAuth token to it. Protected deployment, Finance-only OAuth, authenticated personal review import/readback and browser-reload persistence passed at v0.2.161 on the previous store; see `finance-banking-review.md` for calculation and acceptance boundaries. |
| Health reflection log | `real` | Quick-entry and recent-history views; entries live in the life admin service (`/api/life/v1/health/fast-food`, since v0.2.201). |
| Monzo import | `unavailable` | No Monzo client remains; manual finance controls remain available. |
| Knowledge base and lifestyle tracker | `real` | Owned by the Spring knowledge service (`/api/knowledge/v1/knowledge` and `/lifestyle`): one record per change, entries move between topics without recreation, and lifestyle moves and reorders are worked out by the service (moving between the avoid and practise families restarts the status). |
| Projects reference hub | `real` | Searchable Pinned, Projects, and Archived sections expose links, repositories, documentation, display-only prerequisites, and portable guidance. Shared catalogue metadata is keyed by stable `catalogKey`. Projects and wiki pages are owned by the Spring knowledge service (`/api/knowledge/v1/projects`), which normalises records and keeps each section's order; the Inventory MCP resolves projects there. |

## Removed features

Removed on 2026-09-26 (v0.2.200): the Lina assistant (Chat, hosted OpenAI and Ollama planning, billing, conversation export, activity log and undo, AI diagnostics), voice (wake word, speech recognition and output, Deepgram, ElevenLabs), Life Hero (progression, dashboard companion, daily adventure, motivational voice, concept artifact), its evidence sources (GitHub App integration, Apple Health movement import, Elif B manual evidence), and the unused browser Monzo client. Their code, Edge Functions (`assistant-openai`, `assistant-openai-billing`, `assistant-speech`, `github-life-hero`), database objects and account records (`conversations`, `assistantCorrections`, `assistantActivityLog`) were deleted, not migrated. Stored settings from earlier releases that name these features are ignored.

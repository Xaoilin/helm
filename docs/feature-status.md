# Feature Status

Use this matrix when updating documentation or UI copy. `real` means the hosted website has an implemented path; `paused` means provider work is intentionally disabled; `unavailable` means there is no supported connection; `contract-only` means a reviewed implementation boundary exists but no connector is live; `placeholder/simulated` means the integration is intentionally not presented as live; `required-gap` means policy requires the capability but the implemented path is not yet available.

| Area | Status | Notes |
| --- | --- | --- |
| Hosted GitHub Pages website | `real` | The browser website is the only supported Sabah One product runtime. Release detection runs before account loading, with existing pending-write, editor, draft, and hidden-tab reload guards. Failed initial account loads expose an explicit Retry connection and truthful bounded-retry guidance. Protected promotion, Pages and Supabase deployment, and handoff verification require the current candidate's tested tree and latest successful evidence; missing or stale receipts fail closed. |
| Supabase account persistence | `real` | Authenticated RLS reads, semantic mutations, idempotent receipts, tombstones, explicit ordering, private account Broadcast, and version-gap recovery make Supabase authoritative. KAN-313 separates Realtime notifications from HTTPS readiness, with independent bounded channel retry and version reconciliation. KAN-316 makes the visible/online version safety check run every ten minutes; Broadcast and foreground/reconnect reconciliation remain immediate and coalesced, with no full snapshot reload for an unchanged version. KAN-317 limits each database/channel recovery cycle to five jittered retries, pauses automatic database triggers after failure, and resumes on foreground, online or explicit retry. Recovery probes before snapshot loading; failed channels are removed to stop SDK retries. Supabase Auth retains its built-in single-flight/backoff behavior, with late bootstrap results unable to replace newer auth events. Transient failures retain confirmed same-account data and drafts with freshness notices; invalid account authorization and account changes fail closed. No offline writes or persistent account-data cache. |
| Page-scoped account loading | `real` | KAN-318 loads shared reminder, reward and timer dependencies plus the active page through an atomic scoped read. Deferred providers remain unloaded; same-account confirmed memory has ten-minute per-dataset freshness, and fresh revisits reuse it. KAN-319 keeps current page demand separate from visited cache: private notifications and missed-event metadata refresh only changed needed collections, invalidate inactive cache, and reconcile missed Vault metadata. Local confirmed writes remain immediate; duplicate/out-of-order events cannot hide changed scopes. Invalid authorization/account changes clear memory; existing bounded recovery remains the only automatic retry owner. See `page-loading.md`. |
| Encrypted Secrets vault | `real` | The signed-in Secrets surface stores searchable account metadata and encrypted values through Supabase Vault RPCs. Values are masked, revealed one at a time, cleared from browser UI state when hidden or the session changes, and excluded from records, Broadcast, logs, and exports. Archive and Restore are reversible; bulk export, sharing, autofill, and permanent deletion are absent. |
| Google Calendar OAuth | `real` | Multi-account Calendar connects through Google's consent popup; the calendar service exchanges the code through the hosted credential function, which keeps refresh credentials. Reconnect is explicit and account-scoped and never replaces the Sabah One session. |
| Supported integration setup | `real` | The offered Google Calendar integration always shows; the profile service (`/api/profile/v1/integrations`) holds each provider's saved connection record (Google only), and the retired `integrations` account collection is no longer read or written. The display shows one supported card per provider and never saves its filtered projection. Missing Google deployment configuration points to the site operator, not a nonexistent Settings field. |
| Google Calendar sync | `real` | The Spring Boot calendar service mirrors Google (60 days back, a year ahead) when Calendar loads stale, every 15 minutes while open, and on **Sync**. A calendar that fails keeps its events; accounts show `needs_reconnect` when Google refuses the credential. Event writes to Google calendars go to Google first and are shown only once confirmed; read-only calendars cannot take events. |
| Google Calendar diagnostics | `real` | Accounts show sync time, sync errors and reconnect state; Debug shows calendar-service and database health. |
| Manual calendar accounts | `real` | Local accounts, calendars and events live in the calendar service; every change is confirmed by the service before it shows. |
| Account app time zone | `real` | Settings supports an optional validated IANA zone with `Automatic` browser fallback. Generic app and Calendar time use one resolver; prayer calculations remain bound to the timetable zone and mismatches are labelled. |
| Tasks daily rollover | `real` | Completed daily habits reopen and a missed streak resets once per day whichever page is open, including when the day changes while the app stays open. Tasks "today", due dates, and habit reward days follow the app time zone; prayer tasks and their outcomes follow the prayer timetable date and wait until it is known. Rules live in `src/services/taskModel.ts`; `useDailyTaskRollover` is mounted once in the provider tree. |
| Recoverable core interactions | `real` | Secret, Trip wizard and Task editors confirm dirty dismissal and retain existing save semantics; the shared dialog hook manages focus and Escape. Calendar and Knowledge open actions are native buttons with separate actions; More contains and returns focus. Health removal requires confirmation. |
| Operational diagnostics | `real` | Debug → Operations shows a bounded redacted session timeline, disconnect/read/write counters and correlated recovery timings, with JSON export. An independent bounded queue sends normalized metadata with the user's bearer token to the profile service (`/api/profile/v1/operational-events`), which turns it into metrics; the Supabase `operational-events` function is retired. Account changes clear local diagnostics; collection failure never gates product operations. Scheduled public synthetic probes publish actionable GitHub status and retained receipts without a live user session. See [availability operations](availability-operations.md) for retention limits, controlled faults, infrastructure evidence and recovery objectives. KAN-321 adds a matched workload receipt and protected deployed-frontend fixture proof; see [workload verification](sync-workload-verification.md) for the evidence boundaries. |
| Global Inventory | `real` | Account-backed Owned and Needed records support search, filters, dimensions, specifications, stock changes, acquisition, archive, and reviewed multiline import. Projects link to the same catalogue by stable key. |
| Inventory planning boundary | `real` | The authenticated `sabah-one-inventory-mcp` Edge Function exposes seven narrow Inventory tools through Supabase OAuth, RLS, and dedicated RPCs. It does not expose Secrets, finance, calendars, chats, settings, or broad mutations. |
| Employment application tracker | `real` | The account-backed Employment tab opens with a compact active-application overview grouped by company, coloured stage labels, next steps, and a visible last-updated date sourced from recorded recruiting activity. All includes closed applications; search and optional filters narrow the list. Each role expands its full details, compensation, remote evidence, notes, editor, and contact history directly beneath that application. The same account-owned application IDs, semantic mutations, and three confirmed seed records are retained; import timestamps do not masquerade as recruiting dates. |
| Employment external agent access | `real` | Six semantic application/history tools use a separate Employment OAuth approval and account-scoped RPCs. Browser and agent edits share semantic mutations; retries are idempotent and revocation blocks subsequent access. Scheduled Codex agents reconcile recruiting sources after their Employment connection is authorized. |

## Removed features

Removed on 2026-09-26 (v0.2.200): the Lina assistant (Chat, hosted OpenAI and Ollama planning, billing, conversation export, activity log and undo, AI diagnostics), voice (wake word, speech recognition and output, Deepgram, ElevenLabs), Life Hero (progression, dashboard companion, daily adventure, motivational voice, concept artifact), its evidence sources (GitHub App integration, Apple Health movement import, Elif B manual evidence), and the unused browser Monzo client. Their code, Edge Functions (`assistant-openai`, `assistant-openai-billing`, `assistant-speech`, `github-life-hero`), database objects and account records (`conversations`, `assistantCorrections`, `assistantActivityLog`) were deleted, not migrated. Stored settings from earlier releases that name these features are ignored.

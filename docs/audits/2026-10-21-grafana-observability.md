# Grafana observability audit — 21 October 2026

**Verdict: the requested coverage is not met.** Sabah One has useful service metrics, but major failures can remain invisible in Grafana. Closing the gaps requires metrics, searchable logs, correlated traces, browser monitoring, external probes, and tested notifications. Converting every log line or request identifier into a metric would increase cost and reduce reliability.

This was a read-only production audit. No application, infrastructure, dashboard, alert, credential, or billing configuration was changed. The proposed work below is not implemented or accepted.

## Signal correctness findings

1. **Percentiles need an explicit contract.** The services dashboard uses `max` over exported per-process p95 values. That can represent the worst process/status meter's p95, but is not the p95 of combined traffic. The HTTP bucket query returned only `le="+Inf"` (four series), so it cannot supply a useful classic-histogram percentile. Add a deliberately small set of latency/SLO boundaries or a verified native histogram, validate its OTLP → Grafana representation, then derive fleet percentiles from that. Do not blindly enable dozens of buckets on every timer. [Micrometer explains the aggregation limitation](https://docs.micrometer.io/micrometer/reference/concepts/histogram-quantiles.html).
2. **Resource identity is incomplete.** All nine JVM samples have `job="unknown_service"` and `service_name="unknown_service"`. The custom `service` tag distinguishes dashboards, and the two live gateways have distinct `instance` labels; the other seven services lack that instance label. Set proper OpenTelemetry service/environment/version and bounded instance identity consistently before extending logs/traces or adding replicas.
3. **Absence and stale values can look healthy.** Business refresh failures retain prior values; the last-success signal exists but neither audited dashboard queries it. The snapshot's seven refresh ages were 148–273 seconds, consistent with the five-minute quiet cache, not a failure. Several business panels use `or vector(0)`, which can also hide missing telemetry. Pair values with freshness/availability rather than interpreting missing data as zero.
4. **Browser telemetry is deliberately lossy and can duplicate.** Source limits are 200 local events, 50 queued, 60 events/minute, batches of 10, a 10-second flush and 3-second deadline, with up to three attempts. This protects the app. Drops/sink failure remain local, successes and failures share the same rate allowance, and the recorder increments for every received event without deduplicating event IDs. A lost response followed by retry can overcount. Export aggregate loss/transport status when possible, preserve failure capacity, and define whether counters measure unique events or accepted ingestion attempts. Offline/crashed clients still cannot guarantee delivery.
5. **Dashboard titles overstate some measurements.** “Pages you opened per day” counts backend GET requests, including background work, retries and agent traffic; it is not a page-view counter. Distinguish user actions, request attempts and completed writes. Count scheduled execution separately from useful job completion. Keep error-status counters and searchable error details as separate signals.
6. **Some business labels are not structurally bounded.** Calendar names and inventory categories are copied from database strings into tags. Current cardinality is small, but no `MeterFilter` cardinality ceiling was found. Map operational labels to bounded categories, avoid private calendar names in infrastructure telemetry, and enforce caps before collection expands.

## Collection overhead and data protection

Current evidence supports retaining the existing controls: metrics export once per minute; business reads after committed changes or a five-minute quiet age; bounded browser batches; small database pools. The prior collection-overhead fix must not be undone by adding SQL polling for every new panel.

The 2,417 service-labelled series comprise 624 Spring Security series (25.8%), 530 JVM, 236 HTTP, 150 repository, 144 scheduled execution, 133 Hikari, 121 business/client, 99 Rabbit client, 8 Rabbit listener and 372 other. These are counts, not measured CPU or monetary cost. Review the value of fine-grained filter-chain meters before adding more detail; do not drop authentication outcomes or remove metrics used by a rule without checking dependencies.

Both hosts have approximately 3.8 GiB RAM. At inspection they reported approximately 1.9/1.5 GiB available memory and 48%/64% root-disk occupancy. These are single samples, not capacity or overhead benchmarks. Docker uses `json-file`; per-container rotation options are empty and no daemon configuration file was present. Later privileged size checks found only about 176/196 kB of current container logs; the initial wildcard size check failed and its zero output must not be used. Enable bounded local rotation before increasing log volume.

Recommended starting policy, **proposed and unmeasured**:

| Signal | Collection and limit |
| --- | --- |
| Requests, errors, health, saturation | Unsampled in-process counters/gauges; minute export/scrape for normal signals. External health probes at roughly one minute where affordable. Count each attempt and logical outcome separately. |
| Latency | Histograms on consequential boundaries only, with a small SLO bucket set. Validate units and aggregation. Keep normal API work separate from long-lived streams. |
| Logs | Structured, sanitized failures and useful lifecycle events to Loki. Sample repetitive success/access detail; deduplicate storms with occurrence counters. Bound line size, buffer, retry and disk retention. Log counts alone cannot explain a failure. |
| Traces | Correlate browser → API → queue → database/provider. Sample ordinary successful traffic; use a bounded tail-sampling policy to prefer errors and slow traces. Tail sampling has memory/cost requirements and cannot promise every error survives overload. |
| Browser | Standard browser observability, or a narrow extension of existing telemetry, for errors and user-perceived performance. Evaluate the SDK's bundle/runtime cost. Do not enable session replay or indiscriminate console capture by default. |
| Database | Prefer provider/native cumulative statistics and exported health over new per-request SQL queries. Reuse the Metrics API integration; keep credentials server-side. Provider-log export availability and cost must be checked for the current plan. |
| Pipeline | Fixed memory/CPU/disk and queue caps; asynchronous batches and timeouts; loss/retry/export counters. Grafana unavailability must not block user requests or create unbounded retries. |
| Labels and privacy | Allowlist service, environment, route template, method, bounded status/reason/job/queue/provider. No user IDs, request IDs, trace IDs, raw paths/query strings, calendar titles, email, tokens, SQL parameters or account data as metric labels. Sanitize log/trace attributes before export. Correlation IDs belong in controlled log/trace fields. |

Use one small collector per host for infrastructure/log collection where practical; keep existing Micrometer metrics export unless changing it brings a demonstrated benefit. Avoid duplicate scraping/exporting of the same signal. [Alloy supports metrics/logs/traces processing](https://grafana.com/docs/grafana-cloud/send-data/alloy/introduction/how-alloy-works/), including a [memory limiter with explicit backpressure/drop behavior](https://grafana.com/docs/alloy/latest/reference/components/otelcol/otelcol.processor.memory_limiter/). The supported [Supabase integration](https://supabase.com/docs/guides/observability/metrics/grafana-cloud), [RabbitMQ monitoring](https://www.rabbitmq.com/docs/4.1/monitoring), [Caddy metrics](https://caddyserver.com/docs/metrics) and [Faro browser instrumentation](https://grafana.com/docs/grafana-cloud/observe-and-act/monitor-applications/frontend-observability/) are implementation candidates, not installed components.

Before acceptance, compare the same representative workload with and without added collection. A proposed initial stop threshold is more than 5% regression in p95 useful-request latency or workload-normalized CPU, measured beyond run-to-run variation. Choose and record an absolute collector memory/disk budget within the actual host headroom. Include bytes exported, active series, database reads, browser bytes/long tasks, buffer drops and failure-storm behavior. Current evidence does **not** quantify those overheads, establish a safe final budget, or prove the separate Supabase daily-egress target.

## Remediation order and acceptance

These are blockers to the requested visibility, not evidence of a current production outage. No P0 outage was established by this audit.

| Stage | Scope | Required proof |
| --- | --- | --- |
| 1 — Trust the monitoring | Resource identities; expected-target/freshness/loss signals; private collector endpoints; bounded buffers/log rotation; real notification route | A controlled missing-target and test-alert exercise reaches the intended recipient; pipeline outage cannot block the app or fill memory/disk. |
| 2 — Cover infrastructure | Host/container, Caddy, both brokers, Supabase metrics/provider logs, Edge/MCP boundary, external Pages/service/TLS probes | An inventory shows each expected target reporting. Isolated test-environment proxy error, queue backlog, database fault and failed probe appear with the correct source and trigger the intended alert. |
| 3 — Cover user operations | Browser crash/unhandled error/network/performance; shared client attempts/outcomes; outbound HTTP; scheduled-job/reminder/sync outcomes; bounded JDBC timing and cross-boundary traces | A representative successful user action and a controlled failure can be followed from the browser through the service and dependency to confirmed outcome. Browser permission-denied/offline delivery is represented honestly. |
| 4 — Prove accuracy and overhead | Histogram contract; freshness-aware dashboards; ingestion duplicate/loss semantics; correct page/action labels; measured retention/cardinality and workload cost | Known test counts match the documented semantics; combined percentiles are valid; the comparable overhead gate passes and telemetry/export failure remains bounded. |

The core acceptance oracle is: **for every inventory boundary, induce a representative safe failure in an isolated environment, observe its signal in Grafana within the declared detection window, verify the notification, and show collection remains within its measured budget.** Production verification then checks the exact approved release, target inventory, freshness and benign live transactions through the protected Sol-owned delivery path. No production faults or load tests were injected here.

There are unavoidable limits: a browser that never boots or loses all connectivity cannot send its own final error; a provider may not expose every internal signal; sampling, finite buffers and backend outages can lose detail. Independent probes, telemetry-loss signals and explicit detection windows provide defensible coverage. An unqualified “100% of every issue” claim would remain false.
